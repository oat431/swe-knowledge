# Working with Engineering

> Effective product management requires strong engineering relationships. Understanding engineering culture, speaking their language, and respecting their expertise enables productive collaboration.

## Why Engineering Relationships Matter

**Without strong relationships:**
- Miscommunication and misunderstandings
- Adversarial dynamics
- Slow decision-making
- Poor morale

**With strong relationships:**
- Clear communication
- Collaborative problem-solving
- Fast decisions
- High morale

## Understanding Engineering Culture

### Engineering Values

**What engineers care about:**

**Technical excellence:**
- Clean code
- Good architecture
- Quality practices
- Continuous learning

**Problem-solving:**
- Interesting challenges
- Creative solutions
- Technical depth
- Impact

**Autonomy:**
- Freedom to choose approach
- Ownership of technical decisions
- Space to think
- Trust from leadership

**Impact:**
- Building things that matter
- Seeing work used
- Making a difference
- Technical growth

### Engineering Concerns

**What worries engineers:**

**Technical debt:**
- Accumulating shortcuts
- Unmaintainable code
- Fragile systems
- Future pain

**Unclear requirements:**
- Changing scope
- Ambiguous goals
- Solution without problem
- Rework

**Unrealistic timelines:**
- Impossible deadlines
- Quality sacrifice
- Burnout risk
- Corner cutting

**Lack of context:**
- Why we're building this
- How it fits strategy
- What success looks like
- User impact

## Building Relationships

### 1. Show Respect

**Demonstrate respect for engineering:**

**Acknowledge expertise:**
```
Good: "What's the best technical approach for this?"
Bad: "Just use MongoDB, everyone uses it"
```

**Value their input:**
```
Good: "What are the technical risks we should consider?"
Bad: "Don't worry about that, just build it"
```

**Trust their judgment:**
```
Good: "You know the system best, what do you recommend?"
Bad: "I read that we should do it this way"
```

### 2. Learn the Language

**Understand technical vocabulary:**

**Basic concepts:**
- Frontend vs. backend
- API and integration
- Database and queries
- Deployment and release
- Testing (unit, integration, e2e)
- Monitoring and logging

**Common terms:**
- Refactoring (improving code structure)
- Technical debt (shortcuts that cost later)
- Scalability (handling more load)
- Reliability (system uptime)
- Performance (speed and efficiency)

**Ask when unsure:**
```
"I'm not familiar with that term, can you explain?"
"What does that mean for our users?"
"Can you help me understand the implications?"
```

### 3. Provide Context

**Give engineering the why:**

**Business context:**
```
"We're building this feature because:
- Customer interviews show 80% need this
- Competitors all offer it
- It supports our strategic goal to improve retention"
```

**User context:**
```
"Here's who will use this:
- Customer service reps (primary)
- Managers (secondary)
- They'll use it 10+ times per day
- Speed is critical for their workflow"
```

**Success context:**
```
"We'll know this is successful when:
- Call handling time decreases by 30%
- User satisfaction increases to 4.5
- Adoption reaches 80% in first month"
```

### 4. Be Available

**Make yourself accessible:**

**Regular interactions:**
- Attend standups (listen, don't dominate)
- Join sprint planning (clarify, don't dictate)
- Participate in retrospectives (learn, improve)
- Informal conversations (build rapport)

**Quick responses:**
- Answer questions promptly
- Clarify requirements when asked
- Make decisions when needed
- Remove blockers

**Office hours:**
- Set regular times for questions
- Be available for ad-hoc discussions
- Encourage engineering to reach out

### 5. Celebrate Success

**Recognize engineering achievements:**

**Public recognition:**
- Sprint reviews: Highlight technical achievements
- All-hands: Celebrate releases
- Company updates: Share technical wins

**Private recognition:**
- Thank individuals for great work
- Acknowledge extra effort
- Recognize technical excellence

**Tangible recognition:**
- Advocate for promotions
- Support conference attendance
- Enable learning time

## Collaboration Patterns

### 1. Three Amigos

**Product + Engineering + Design collaboration:**

**Process:**
```
1. Product defines problem and goals
2. Design explores user experience
3. Engineering assesses feasibility
4. Together: Define solution
```

**Benefits:**
- Multiple perspectives
- Better solutions
- Shared ownership
- Faster decisions

### 2. Technical Spikes

**Explore technical approach:**

**When to use:**
- Unclear feasibility
- Multiple approaches
- High uncertainty
- New technology

**Process:**
```
1. Define question (Can we do X?)
2. Time-box exploration (1-2 days)
3. Engineering investigates
4. Share findings
5. Decide on approach
```

### 3. Pair Work

**Product and engineering together:**

**Activities:**
- User interviews (together)
- Support calls (listen together)
- Data analysis (review together)
- Planning sessions (collaborate)

**Benefits:**
- Shared understanding
- Better decisions
- Stronger relationships
- Faster alignment

## Communication Best Practices

### 1. Be Clear and Specific

**Avoid ambiguity:**
```
Bad: "Make it faster"
Good: "Page load under 2 seconds for 95% of users"
```

**Define success:**
```
Bad: "Improve user experience"
Good: "Reduce task completion time by 30%"
```

### 2. Focus on Problems, Not Solutions

**Let engineering solve technical problems:**
```
Bad: "Add a dropdown with these 5 options"
Good: "Users need to select from multiple choices,
      what's the best UX pattern?"
```

**Explain the why:**
```
Bad: "Use React for the frontend"
Good: "We need a responsive, interactive interface
      that works across devices"
```

### 3. Listen Actively

**Understand engineering perspective:**
- Ask questions
- Paraphrase to confirm
- Acknowledge concerns
- Incorporate feedback

**Example:**
```
Engineering: "This will take 4 weeks"
PM: "That's longer than expected, help me understand why"
Engineering: "We need to refactor the database schema"
PM: "What happens if we don't refactor?"
Engineering: "Performance issues, harder to maintain"
PM: "Got it, let's plan for the refactor"
```

### 4. Adapt Your Style

**Match engineering preferences:**

**Some engineers prefer:**
- Detailed written specs
- Visual diagrams
- User stories
- Technical documentation

**Ask:**
```
"How do you prefer requirements documented?"
"What level of detail is most helpful?"
"How can I best communicate changes?"
```

## Common Relationship Mistakes

### 1. Us vs. Them

**Mistake:**
- Product vs. engineering
- Business vs. technical
- Adversarial dynamics

**Fix:**
- One team, shared goals
- Collaborative language
- Joint problem-solving

### 2. Not Understanding Context

**Mistake:**
- Don't know technical challenges
- Ignore system constraints
- Unrealistic expectations

**Fix:**
- Learn about the system
- Ask about challenges
- Understand constraints

### 3. Changing Requirements Constantly

**Mistake:**
- Frequent scope changes
- Mid-sprint changes
- No stability

**Fix:**
- Stable sprint commitments
- Clear change process
- Respect planning

### 4. Not Following Up

**Mistake:**
- Define requirements, disappear
- Don't answer questions
- Not available for clarification

**Fix:**
- Stay engaged
- Be available
- Follow through

### 5. Taking Credit, Not Sharing

**Mistake:**
- Claim success as product win
- Ignore engineering contribution
- Blame engineering for failures

**Fix:**
- Share credit
- Celebrate together
- Own failures jointly

## Senior-Level Engineering Relationships

1. **Strategic partnership**
   - Not just tactical collaboration
   - Contribute to technical strategy
   - Align product and engineering vision

2. **Relationship leadership**
   - Build strong relationships
   - Resolve conflicts
   - Foster collaboration culture

3. **Organizational influence**
   - Advocate for engineering
   - Secure resources
   - Remove organizational barriers

4. **Advanced collaboration**
   - Complex technical challenges
   - Cross-team coordination
   - Technical transformation

## Metrics

- Collaboration effectiveness (team assessment)
- Decision speed (time to alignment)
- Requirement clarity (engineering feedback)
- Relationship health (regular check-ins)
