# Reading the Career Path Map

> **Core skill:** Using this vault's map to frame options and trade-offs

## What Changes from Junior to Mid

A junior engineer reads a career map the way a traveler reads a departure board: a list of destinations, one of which must be picked. A mid-level engineer reads it as a terrain map: a set of options with real trade-offs, entry points, and combinations, none of which is a one-way ticket. The skill shift is from collecting titles to framing choices — knowing what each path actually demands day to day, what it gives up, and how to test interest before committing.

| Aspect | Junior | Mid |
|--------|--------|-----|
| Reading the map | Sees 19 role names and picks the most impressive one | Groups paths into families and compares what each family's work feels like |
| Role titles | Treats titles as standardized definitions | Knows titles vary by organization and reads outcomes and scope instead |
| Choosing a direction | Waits for certainty or copies a mentor | Shortlists two hypotheses and tests each with small evidence |
| Level sections | Skips straight to the senior headline | Reads level deltas to see what the work demands at each stage |
| Combining paths | Assumes one path must fit perfectly | Builds a base path plus a specialty deliberately |
| Market fit | Assumes the global map matches local demand | Checks local openings and title usage against the map before planning |
| Revisiting | Reconsiders only when unhappy | Revisits on a schedule, with evidence from the last test |

## Core Frameworks

### The Map's Structure: Families and Questions

The vault maps 19 role paths reachable from software engineering. Each path is a folder with an overview plus capability-area modules; each overview states the role's purpose, outcomes, capability areas, differences from neighbors, and evidence of progress.

| Family | Paths | The Main Question |
|--------|-------|-------------------|
| Technical individual contributor | Senior Software Engineer, Staff Engineer, Principal and Distinguished Engineer | Can I own more and influence further without managing people? |
| Technical leadership | Tech Lead, Software Architect | Can I hold a team's or a system's technical coherence? |
| Specialist engineering | SRE and Platform, Security, Data and ML, Quality and Test, Applied AI, Forward Deployed Engineer | Which deep competency do I want to be hired for? |
| People leadership | Engineering Manager | Do I want outcomes through other people's growth and output? |
| Delivery leadership | Technical Program Manager, Project and Program Manager | Is coordinating complex work itself the craft I want? |
| Product and business | Product Manager | Do I want to decide what gets built and why? |
| Enterprise and customer-facing | Solutions and Enterprise Architect | Do I want to connect technology to business and enterprise change? |
| Communication and ecosystem | Developer Advocate and Technical Consultant | Do I want to teach, persuade, and grow a user community? |
| Independent practice | Independent Consultant and Technical Founder | Do I want to build a business on my engineering expertise? |

### Reading One Path Before Testing Interest

| Part of a Path | What It Tells You | How to Use It for Fit |
|----------------|-------------------|-----------------------|
| Overview opening | The role's purpose and center of gravity | Check whether the stated outcomes excite you, not the title |
| Capability areas and topic notes | The actual skills the work is made of | Sample two topic notes; do the tasks sound like good days? |
| Level-delta sections | How the work changes from junior to mid to senior | Test whether the mid-level version of the work appeals, since that is the near-term reality |
| Differences from nearby paths | The boundary with neighbors you might confuse | Read these to discover which role you actually want |
| Evidence and artifacts | What progress looks like in outputs | Ask whether you would enjoy producing those artifacts weekly |
| Connections and next steps | Where the path leads and combines | Look for your second path here; paths are designed to be combinable |

### Maps, Not Rails: Combination Patterns

| Combination | What It Looks Like in Practice | Watch Out For |
|-------------|-------------------------------|---------------|
| Software Engineer plus reliability specialty | You own your service's dashboards, on-call, and incident reviews while staying on a product team | Being the permanent firefighter and losing feature depth |
| Software Engineer plus security focus | You do threat modeling and secure design for your team's features | Security becoming a side hobby with no mandate or time |
| Software Engineer plus data or AI | You build the pipelines or model-backed features your product needs | Tool churn outrunning your fundamentals |
| Software Engineer plus tech-lead duties | You hold technical coherence for one team alongside your own delivery | Leading by exhaustion instead of delegation |
| Software Engineer plus product sense | You join discovery, write problem statements, and measure outcomes | Doing a second job without recognition or time |

## In Practice

**Read the map as trade-offs, not as a menu of titles.** Every path buys something with something else: staff-track influence costs people-management scope, management costs deep IC time, field roles cost travel and schedule stability. Write the trade-off in one sentence per candidate path before you write anything flattering about it. A direction you cannot state a cost for is a direction you have not actually read.

**Use level deltas to test interest, not the top-level headline.** The daily work at mid-level is what you would actually do for the next few years, so read the junior-to-mid and mid-to-senior changes in each topic note and ask whether the harder version of the work appeals. Many people are attracted to the senior title and repelled by the senior tasks: more ambiguity, more review, more writing. The delta sections are where that shows.

**Treat every path as reachable and none as mandatory.** This map starts at Software Engineer and shows 18 onward paths; entry points and next steps are documented per path, so nothing on the map requires a specific degree, employer, or lineage. Choosing a specialty narrows your search, not your eligibility. The only irreversible move is refusing to choose anything while the years pass.

**Combine a base path with a specialty instead of forcing one perfect fit.** Real careers look like Software Engineer plus reliability, or Senior Engineer plus tech-lead duties — the map's families are designed to interlock. Pick a base that keeps you employable and a depth bar that makes you distinctive, then let evidence from work decide how the mix shifts.

**Check your local market against the global map before you plan around it.** The map is an abstraction of how these roles behave across the industry; in your country, industry, and company size, titles may be flattened, renamed, or absent, and demand for security, data, or platform roles may be concentrated in a few sectors. Read local job postings for the two roles you shortlisted and note what scope they actually describe. Plan against the work you can get, then keep the map for direction.

**Frame each option with a one-sentence hypothesis and a test.** "I think I would like security work because I enjoyed threat modeling in the last design" is a hypothesis; "I will run threat modeling for the next feature and check whether I volunteer for it again" is a test. This habit converts anxiety into a queue of small experiments.

## Practical Exercise

Practice reading the map end to end for your own decision:

1. Open the career path overview and list the nine families from memory after closing it; write one sentence on the trade-off each family makes.
2. Pick two candidate paths and read each path's overview in full; summarize each in three sentences: purpose, outcomes, and what it gives up.
3. From each candidate, open two topic notes and read only the "What Changes from Junior to Mid" sections; note which daily changes appeal and which do not.
4. Write one energizing and one draining element per candidate, drawn from specific past work, not from the role descriptions.
5. Check real local job postings for both candidates: record the scope described, the title used, and whether it matches the map's description.
6. Design one small fit test per candidate that you can run inside your current job within a quarter.
7. Write a one-page decision memo: hypothesis, test, evidence so far, revisit date.

## Practical Applications

- [ ] I can name the nine families and which two of them my shortlist sits in
- [ ] My shortlist contains exactly two candidate paths, each with a stated trade-off
- [ ] I have read level deltas for both candidates, not just their overview headlines
- [ ] I can explain what each candidate gives up in one honest sentence
- [ ] At least one fit test per candidate runs inside my current job this quarter
- [ ] I have checked local job postings and know where the map and my market disagree
- [ ] My plan keeps a base path plus one depth bar rather than a single all-in bet
- [ ] A revisit date is on my calendar, with the evidence I will bring to it

## Common Pitfalls

| Pitfall | Why It Fails | Better Approach |
|---------|--------------|-----------------|
| Shopping by title | Titles vary by organization and hide the real day-to-day work | Read the outcomes and scope in each path overview first |
| Reading only the overview headline | The headline sells the peak of the role, not the years of ordinary work | Sample topic notes and level deltas before deciding |
| Assuming the map matches your local market | Demand and titles differ by country, industry, and company size | Check local postings and plan against real scope |
| Choosing from one bad quarter | A rough on-call rotation or a failed project reads like a verdict | Sample several projects over months before concluding |
| All-in on one path overnight | Fragile skills and a narrowing option set with no evidence yet | Keep a base path and add one depth bar at a time |
| Reading paths as a ranking | The map is a set of trade-offs, not a ladder of prestige | Compare costs honestly; several paths are lateral, not lower |

## Success Indicators

- You can describe two candidate paths with the trade-off each one makes
- You read level deltas before forming an opinion about a role
- You can point to where your local market differs from the map and have planned around it
- Each candidate has a small test running inside your current job
- Your plan names a base path plus one depth bar instead of a single destination
- You revisit the map on a schedule with evidence, not only when frustrated
